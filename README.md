# Ticket Events API

פרויקט קטן שמדגים API לניהול פניות ואירועים. הוא נבנה ב־ASP.NET Core 8 עם Controllers, ‏Entity Framework Core ו־SQLite. אפשר ליצור פנייה, לעדכן את הסטטוס שלה, ולשלוח אירועים בבטחה גם אם אותה בקשה מגיעה יותר מפעם אחת.


## הרצת השירות

פתחו PowerShell בתיקייה שבה נמצא `TicketEvents.sln`, והריצו:

```powershell
dotnet restore .\TicketEvents.sln
dotnet run --project .\src\TicketEvents.Api
```

כשהשירות עולה, הטרמינל מציג את הכתובת המקומית שלו, למשל `http://localhost:5026`. השתמשו בכתובת שמופיעה אצלכם. כדי לעצור את השירות, לחצו `Ctrl+C`.

אם מופיעה הודעה שהפורט כבר בשימוש, עצרו קודם הרצה קודמת של השירות. אפשר גם לבחור פורט אחר:

```powershell
dotnet run --project .\src\TicketEvents.Api --urls http://localhost:5027
```

בהפעלה הראשונה נוצר קובץ `tickets.db` בתיקיית העבודה. הנתונים נשמרים בו גם לאחר עצירת השירות.

## מה אפשר לעשות עם ה־API

### לשלוח אירוע — `POST /api/ticket-events`

אירוע `Created` יוצר פנייה חדשה. אירוע `StatusChanged` מעדכן את הסטטוס ואת זמן העדכון שלה.

דוגמה ליצירת פנייה:

```json
{
  "eventId": "evt-1001",
  "ticketId": "T-501",
  "customerId": "C-100",
  "type": "Created",
  "status": "Open",
  "subject": "Customer cannot log in",
  "occurredAt": "2026-10-20T10:30:00Z"
}
```

דוגמה לשינוי סטטוס של פנייה קיימת:

```json
{
  "eventId": "evt-1002",
  "ticketId": "T-501",
  "type": "StatusChanged",
  "status": "InProgress",
  "occurredAt": "2026-10-20T11:00:00Z"
}
```

בכל אירוע נדרשים `eventId`, ‏`ticketId`, ‏`type`, ‏`status` ו־`occurredAt`. סוגי האירועים הנתמכים הם `Created` ו־`StatusChanged`; הסטטוסים הנתמכים הם `Open`, ‏`InProgress` ו־`Resolved`. ביצירת פנייה צריך לשלוח גם `customerId` ו־`subject`.

התגובות העיקריות:

- `201 Created` — הפנייה נוצרה.
- `200 OK` — האירוע עובד, או שכבר התקבל קודם. במקרה של כפילות התשובה כוללת `duplicate: true`.
- `400 Bad Request` — חסר שדה חובה או שנשלח ערך לא נתמך.
- `409 Conflict` — האירוע לא מתאים למצב הפנייה, למשל ניסיון לשנות סטטוס לפני שהפנייה נוצרה.

ה־`eventId` הוא מפתח ייחודי במסד הנתונים. כך גם שתי בקשות שמגיעות במקביל לא יכולות לשמור את אותו אירוע פעמיים. שמירת האירוע ועדכון הפנייה מתבצעים באותה טרנזקציה.

### לקבל את מצב הפנייה — `GET /api/tickets/{ticketId}`

הנקודה הזו מחזירה את מזהה הפנייה והלקוח, הנושא, הסטטוס הנוכחי וזמן העדכון האחרון. אם הפנייה לא קיימת, מתקבלת תשובת `404 Not Found`.

לדוגמה:

```text
GET http://localhost:5026/api/tickets/T-501
```

## בדיקה מהירה ב־Postman

השתמשו בכתובת שהופיעה בטרמינל. בבקשות POST בחרו **Body → raw → JSON**.

1. שלחו את דוגמת `Created` ל־`/api/ticket-events`. אמורה להתקבל תשובת `201 Created`.
2. שלחו GET ל־`/api/tickets/T-501`. הפנייה אמורה להופיע בסטטוס `Open`.
3. שלחו אירוע `StatusChanged` עם `eventId` חדש, `ticketId` של הפנייה וסטטוס `Resolved`. התשובה אמורה להיות `200 OK`; GET אמור להראות את הסטטוס החדש.
4. שלחו שוב את אותו אירוע, עם אותו `eventId`, אבל עם סטטוס `Open` ושעת אירוע מאוחרת יותר. התשובה אמורה לציין `duplicate: true`. בדקו שוב עם GET: הסטטוס וזמן העדכון צריכים להישאר כפי שהיו אחרי האירוע הראשון.

אם כבר הרצתם את הדוגמה, בחרו `ticketId` ו־`eventId` חדשים. מסד הנתונים המקומי שומר את הנתונים בין הרצות.

## מה הושלם

- API ב־ASP.NET Core 8 עם Controllers.
- שמירת אירועים ופניות ב־SQLite באמצעות Entity Framework Core.
- בדיקת שדות חובה וערכי `type` ו־`status`.
- יצירת פנייה ועדכון הסטטוס וזמן העדכון האחרון.
- מניעת עיבוד כפול של אותו `eventId`, עם הגנה ברמת מסד הנתונים.
- נקודת קצה לקבלת מצב הפנייה.
- בדיקת אינטגרציה שמוודאת שאירוע כפול נשמר פעם אחת, ושבקשה חוזרת עם תוכן שונה לא משנה את מצב הפנייה או את זמן העדכון. הבדיקה משתמשת ב־SQLite זמני בזיכרון, ולא נוגעת בקובץ הנתונים המקומי.

תור RabbitMQ ו־Worker לא נכללים במימוש. מסד הנתונים נוצר באמצעות `EnsureCreated`; מיגרציות EF Core לא הוגדרו בפרויקט.
